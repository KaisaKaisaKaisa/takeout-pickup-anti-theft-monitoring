# PWA 审计链路卡片语言设计

日期：2026-03-18

## 目标
在已完成的“规则命中 -> 告警 -> 证据详情”审计链路基础上，继续强化链路内部的数据单元表达，让用户不只看到链路结构，还能一眼看懂链路中的每一条记录、每一条告警和每一个动作入口。

这一轮聚焦：
- 卡片级信息层级
- 卡片级状态表达
- 卡片级 hover / 操作反馈

## 范围
- 调整 `apps/pwa/src/app.js` 中以下卡片构建模板的 DOM 结构：
  - `buildRuleMatchCard`
  - `buildAlertCard`
  - `buildDeviceCard`
  - 以及对应的 localized 版本
- 调整 `apps/pwa/src/styles.css` 中针对审计链路卡片的视觉语言
- 在 `apps/pwa/tests/cyber_ui_upgrade.test.js` 中补充卡片级结构与样式断言

## 非目标
- 不修改接口调用、状态逻辑、WebSocket 行为
- 不修改列表挂载 `id`
- 不再重排整个下半段布局

## 当前问题
当前下半段的大面板叙事已经建立，但链路内部的实际数据项仍然是统一的 `li.card`：
- `rule-matches` 中的记录项还像普通日志卡
- `alerts` 中的告警项还缺少明显的等级、状态和动作主次
- `devices` 中的支撑项还没有形成“支撑舱”的低优先级但高可信表达

结果是：
- 用户看到了链路，但还没有看到“高质量链路单元”
- 信息层级在卡片内部仍然偏平
- 高级感主要停留在容器级，还没有下沉到真实数据单元

## 备选方案

### 方案 A：卡片级链路语言统一
对 `rule-matches`、`alerts`、`devices` 三类卡片分别建立明确的卡片骨架和状态表达。

优点：
- 提升最直接
- 卡片级 hover 和操作语言会显著更强
- 与现有审计链路面板形成上下统一

代价：
- 需要动 `app.js` 中的模板字符串
- 要同时维护中英文两套模板

### 方案 B：只强化 CSS，不改卡片结构
保留现有模板，只用 CSS 去做视觉增强。

优点：
- 改动小

问题：
- 没法从根本上提升信息层级
- 很多品牌感只能停留在“表皮”

### 方案 C：只强化告警卡
只动 `alerts`，因为它是链路中段核心。

优点：
- 风险更低

问题：
- 链路起点和支撑区会继续显得弱

## 结论
采用方案 A。

## 设计方案

### 1. `rule-matches` 卡片：审计记录条目
每条命中卡增加更明确的内部结构：
- 顶部：规则名称 + 事件类型
- 中段：规则集、订单、会话、命中时间、抑制状态
- 底部：条件/指标代码块

视觉目标：
- 像“审计追踪记录”
- 抑制状态一眼可见
- 比当前更有时间线与追踪感

### 2. `alerts` 卡片：告警矩阵单元
每条告警卡增加更明确的状态与动作层级：
- 顶部：告警摘要 + 等级
- 中段：状态、时间、订单
- 底部：动作区，强调“取证”为主动作，其他为次动作

视觉目标：
- 像“待处置告警单元”
- 中段信息更像状态面板，而不是简单文本
- 动作区一眼分出主次

### 3. `devices` 卡片：支撑舱节点
设备卡保留简洁，但需要更可信：
- 顶部：设备名 / 摘要
- 中段：类型、状态、更新时间、设备码
- 底部：单一动作

视觉目标：
- 不抢主叙事
- 但一眼看出是“支撑网格节点”

### 4. 共用卡片语言
为三类卡片补充共享结构类：
- 卡片头部容器
- 状态芯片 / 标签
- 元信息网格
- 主动作 / 次动作组

这样样式可以在 CSS 中统一组织，而不是依赖每个列表分别写死。

## 技术约束
- 允许修改 `app.js` 中纯展示模板
- 不允许改业务 API、action 行为、事件处理语义
- 保留现有 `data-action`
- 保留现有列表挂载点和 `data-id`
